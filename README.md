# loadcrash

Crash, late-commit and zombie-run tests for incremental data loads.

This is the code and data behind the paper **"Late Commits and Zombie Runs: A
Study of Watermark Designs for Incremental Data Loads"** (Ian O'Leary, 2026).

loadcrash runs thirteen load patterns (append, upsert, partition overwrite, and
a few file/manifest "lake" layouts) against a synthetic source and checks the
target against the source row by row afterwards. It covers three ways a load
can go wrong:

- **Crashes** at every step boundary, plus real `SIGKILL`s at random moments
- **Late commits**: source transactions that commit after the watermark has
  passed their timestamp (uniform, lognormal or Pareto delays), which is where
  high-watermark extraction quietly drops rows
- **Zombie runs**: a stalled run wakes up after its replacement has finished

It also implements commit-horizon extraction (only read rows older than the
oldest open source transaction), an adaptive lookback window, and three ways
of guarding the watermark write (none, monotonic, compare-and-set).

## Quick start

Requires Python 3.10+. The harness itself uses only the standard library and
SQLite; `pandas`, `matplotlib` and `tabulate` are needed for the analysis.

```bash
pip install -r requirements.txt
python -m unittest discover -s tests          # ~2 s
python experiments/run_all.py --quick         # ~1 min smoke run
python experiments/run_all.py                 # full run (see "Reproducing the paper")
python experiments/analyze.py                 # E1-E4 tables and Figures 1-2
python experiments/analyze_new.py             # E5-E7 tables and Figure 3
```

`run_all.py` overwrites the CSVs in `results/`. To compare a fresh run against
the published results, copy the repository first or check the diff with git.

## Reproducing the paper

The results in the paper were produced on Linux 6.18 with 2 vCPUs,
Python 3.13.16 and SQLite 3.45.1. Every experiment is deterministic for a given
seed except E4, where the kill moment depends on timing, so a rerun of E4 gives
similar but not identical counts.

| Experiment | What it does | Trials | Raw CSV | Used in the paper |
|---|---|---:|---|---|
| E1 | Crash at every crash point of the 11 base patterns | 2,200 | `e1_crash_points.csv` | Section 4.1 |
| E2 | Extraction predicate × late-commit rate | 1,680 | `e2_watermark_lag.csv` | Section 4.2, Figure 2 |
| E3 | Crashes and late data together | 340 | `e3_crash_and_lag.csv` | Section 4.2 |
| E4 | Real `SIGKILL` at a random moment | 2,200 | `e4_sigkill.csv` | Section 4.1, Figure 1 |
| E5 | Zombie interleavings × watermark guard | 1,320 | `e5_zombie.csv` | Section 4.5, Table 3 |
| E5b | Zombie interleavings with commit-horizon extraction | 300 | `e5b_zombie_horizon.csv` | Section 4.5 |
| E6 | Five watermark strategies × three lag distributions | 420 | `e6_strategies.csv` | Sections 4.3–4.4, Table 2, Figure 3 |
| E7 | Commit-horizon extraction with crashes, unkeyed targets | 390 | `e7_horizon_crash.csv` | Section 4.4 |
| | **Total** | **8,850** | | |

To run a single experiment: `python experiments/run_all.py --only e6`.

`results/summary.md` (E1–E4) and `results/summary_new.md` (E5–E7) hold every
number quoted in the paper. The figures in `figures/` are regenerated by the
analysis scripts; `figures/paper/` holds the restyled versions printed in the
paper, drawn from the same summary CSVs.

## Layout

| Path | What it is |
|---|---|
| `loadcrash/source.py` | Synthetic source with late commits and an oldest-open-transaction table |
| `loadcrash/patterns.py` | The 13 load patterns, watermark strategies and guards |
| `loadcrash/harness.py` | Trial runner: crashes, zombie interleavings, freshness tracking, oracle |
| `loadcrash/fuzz.py` | Real-process `SIGKILL` fuzzing |
| `experiments/run_all.py` | Experiments E1–E7 |
| `experiments/analyze.py` | Summaries and Figures 1–2 (E1–E4) |
| `experiments/analyze_new.py` | Summaries and Figure 3 (E5–E7) |
| `results/` | Raw CSVs and summaries from the runs reported in the paper |
| `figures/` | Generated figures; `figures/paper/` has the versions in the paper |
| `tests/` | Unit tests for the patterns and the oracle |

## Patterns

| ID | Pattern |
|---|---|
| A1 | INSERT batch (txn 1), then advance watermark (txn 2) |
| A2 | Advance watermark (txn 1), then INSERT batch (txn 2) |
| A3 | As A1, consumers read through a `SELECT DISTINCT` view |
| A4 | INSERT batch + watermark in one transaction |
| M1 | Upsert on key (txn 1), then watermark (txn 2) |
| M2 | Upsert + watermark in one transaction |
| P1 | Partition overwrite: DELETE, INSERT, watermark as separate transactions |
| P2 | Partition overwrite in one transaction |
| F1 | Write part file, then watermark file; readers list the directory |
| F2 | Write part file, then commit via atomic manifest rename |
| F3 | As F2, but the manifest is overwritten in place |
| M2A | As M2, with a lookback window that grows from the late rows it finds |
| F4 | Delta-style log: commit by creating version N+1 only if it does not exist |

The first eleven (`ALL` in `patterns.py`) are the base patterns used in E1 and
E4. M2A and F4 (`EXTRA`) were added for the late-data and zombie experiments.

## Adding a pattern

Subclass `Pattern` in `loadcrash/patterns.py`, call `ctx.cp("name")` at each step
boundary, list those names in `crash_points`, and add the class to `ALL`. Every
experiment picks it up automatically.
